# Scaffold a new project

Build the skeleton in the order below. Each step ends with something
runnable — do not scaffold all of it and then try to make it work.

Read `/house-style:conventions` and its references for the *why* behind
each choice. This skill is the *order of operations*.

## 0. Decide the store before writing code

Answer, in the README or DESIGN doc, in one paragraph: **Firestore or
Postgres, and why.** Use the decision rule in
`conventions/references/stack.md` — the test is whether the product
needs graph traversal, joins, or multi-row invariants. Getting this
wrong is a rewrite; write the reasoning down so it is not re-argued.

## 1. Workspace skeleton

```
package.json          # private, workspaces: ["packages/*"], no deps but firebase-tools + prettier
packages/schema/      # zod contract; depends on nothing in-repo
packages/frontend/    # ng new here — angular.json lives in the package
packages/backend/     # Cloud Functions, TypeScript ESM, Node 22
packages/e2e/         # Playwright
scripts/              # dev-local.sh, e2e.sh, deploy-functions.sh
firebase.json         # dev stack
firebase.e2e.json     # e2e stack — separate ports, separate database
```

Root scripts, named the same in every project so muscle memory and CI
transfer: `build`, `test`, `gate`, `dev`, `e2e`, plus `seed:dev`.

## 2. The contract package first

Write `packages/schema` before either side. One file per concept, zod v4,
schema value and inferred type sharing a name. Export a collection
registry if the project uses Firestore — the rules generator reads it.

## 3. Backend boundary before handlers

Create `guards.ts` with the `typedCall(schema, handler)` wrapper (auth
first, then zod, then handler) and the ownership assertion, plus
`src/testing/` harness helpers, plus `boundary.spec.ts` pinning the
export set. Then write the first handler against them. Doing this in the
other order produces handlers that each invent their own boundary.

## 4. Rules (Firestore projects)

First decide, **per collection**, whether the client writes it directly
or a function does — the decision rule is in
`conventions/references/data-contracts.md`. Write the answer and its
reason next to the schema. Do not decide it by counting endpoints.

Then write `firestore.rules`: deny by default, `allow write: if false`
for every function-only collection, hand-written authorization for the
rest.

**Only if some collection is client-written**, add the shape generator:
copy `generate-rules.ts` from `ericeslinger/gradebook`
(`packages/migrations/`), point it at those schemas, and add

- `rules:gen` and `rules:gen:check` scripts;
- the `AUTOGENERATED` marker block in `firestore.rules`, with the
  hand-written authorization *around* it;
- `rules:gen:check` in `npm run gate`.

If every write goes through a callable, skip the generator entirely —
the callable boundary is the enforcement point and generated validators
would be dead rules.

Either way, create the `rules-tests` package with a persona per role and
both allow and deny assertions.

## 5. The gate

`npm run gate` = builds + every unit suite + every `typecheck:spec` +
codegen drift checks + the deploy dry-run. Wire each package in as it is
created, not at the end. Every package with specs needs a
`tsconfig.spec.json` and a `typecheck:spec` script, because vitest does
not typecheck.

## 6. Scripts that own their stacks

`dev-local.sh` (one command: database, emulators, seed, `ng serve`, and
Ctrl-C takes it all down) and `e2e.sh` (isolated ports and database,
preflight, readiness waits, seed, Playwright, teardown). Header comments
explain why each is a script rather than config.

## 7. First journey

One Playwright journey for the first real flow, with `personas.ts` and
`fixtures.ts`, plus the axe a11y journey. Queried by role and accessible
name.

## 8. CI

One workflow on `pull_request`: checkout, Node (matching the functions
runtime), Java (the Firestore emulator is a JVM), cache the emulator
jars, `npm ci`, `npm run gate`, rules suites, install the Playwright
browser, `npm run e2e`. Upload traces and video on failure. Gate the job
on the canonical repository so forks stay quiet. Set a timeout and
`concurrency` with `cancel-in-progress`.

## 9. Docs

`README.md` (layout, prerequisites, commands), `CLAUDE.md` (orientation
paragraph naming every other doc, the invariants, the unit-test policy,
the commands), and a backlog file with stable ids. Add `DESIGN.md` and
`PRINCIPLES.md` if the project has an architecture or a thesis worth
arguing about.

## 10. Wire in the house style itself

So every future session — laptop, cloud, or routine — inherits these
conventions, commit to the new repo's `.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "ericeslinger": {
      "source": { "source": "github", "repo": "ericeslinger/claude-skills" }
    }
  },
  "enabledPlugins": { "house-style@ericeslinger": true }
}
```

Cloud sessions install repo-declared plugins at session start; local
sessions pick it up once the folder is trusted. Personal
`~/.claude/skills` does **not** transfer to cloud sessions, which is why
this goes in the repo.
